# T29 배포 전 전송 보안과 외부 호출 예산

## 결정

- 앱은 Google ID 토큰이나 세션 토큰을 보내기 전에 API origin을 검사한다. 운영 빌드는 HTTPS를 요구한다. 개발 빌드에서는 설정에 지정한 `localhost`, IPv4·IPv6 루프백, 사설 IPv4에 HTTP를 허용한다. [개발 주소 예시](../../apps/mobile/README.md)
- 로그인은 16,384바이트, 여행 생성은 100,000바이트, 생활 설정은 30,000바이트, 제약 저장은 256 KiB까지 JSON을 받는다. `Content-Length`가 한도를 넘으면 본문을 읽기 전에 413을 반환한다. 헤더 유무와 관계없이 청크마다 바이트를 세고 초과하는 즉시 읽기를 취소한다. 한도 안의 청크는 UTF-8로 이어서 디코딩한다.
- 같은 서버 런타임의 `GoogleRoutesClient`들이 네 개의 슬롯을 공유한다. 행렬 타일, 구간 재조회, 지도 모양 요청은 도착 순서대로 슬롯을 얻는다. 성공 응답은 본문을 읽은 뒤, 실패 응답은 본문을 취소한 뒤 슬롯을 돌려준다. 네트워크 오류도 슬롯을 반환한다. Google 요청의 10초 타임아웃은 슬롯을 얻고 전송할 때 시작한다.

## 이유

실기기 개발에는 같은 Wi-Fi의 컴퓨터와 통신하는 경로가 필요하다. 개발 빌드에서 호스트까지 확인하면 운영용 자격증명이 공개 HTTP 주소로 전송되는 설정 오류를 차단할 수 있다.

제약 저장은 최대 방문 100개와 출발·도착 UUID를 포함하는 구간 제약 1,000개를 함께 보낼 수 있어 여행 생성보다 큰 한도를 쓴다. 네 경로 모두 실제 바이트를 세므로 길이 헤더가 없거나 잘못 보고된 요청에서도 메모리에 모으는 입력 크기가 제한된다.

동시 요청 한도 4는 기존 지도 모양 조회에서 쓰던 병렬도다. 여러 날짜와 여행이 겹칠 때도 Google 전송 지점 한 곳에서 한도를 적용할 수 있다. 여러 서버 인스턴스를 배포할 때 프로젝트 전체의 사용량은 Google Cloud 쿼터에서 관리한다.

## 대안

- 본문 전체를 읽은 뒤 문자열 길이를 비교하면 한도를 넘는 입력도 메모리에 들어오고 한글 등 여러 바이트인 글자의 크기 차이를 놓친다.
- 일정별로 동시성을 제한하면 동시 사용자 수에 비례해 한 서버가 보내는 요청이 늘어난다. Google HTTP 전송에 한도를 두면 기존 제공자의 캐시·동일 요청 병합과 스케줄러를 수정할 필요가 없다.

## 측정과 회귀 검증

Node 24.22.3, macOS arm64에서 도쿄 3일 일정 두 건을 동시에 계산했다. 각 일정은 별도 제공자와 캐시를 사용하고 모의 Google HTTP 전송마다 5ms를 기다린다. 두 버전을 번갈아 5회씩 실행했다. 시간은 각 실행에서 측정한 값의 중앙값이다.

| 상태 | Google HTTP 호출 수 | 최대 동시 요청 | 호출당 평균 전송 시간 | 두 일정 완료 시간 |
|---|---:|---:|---:|---:|
| `develop` 기준 `c4b3eae` | 84 | 16 | 6.4ms | 94ms |
| T29 한도 적용 | 84 | 4 | 6.3ms | 155ms |

`npx tsx --test apps/server/tests/routes-budget.test.ts`로 측정을 재현할 수 있다. 테스트는 최대 동시 4건, 호출 84회, 변경 전 전체 일정 결과의 SHA-256 일치를 검사한다. 경과 시간은 실행 환경에 따라 달라져 관측값으로 기록한다. 지연된 응답 본문을 읽는 동안에는 다른 요청이 대기하며 파싱 오류 뒤에도 다음 요청이 진행되는지 별도로 검증한다.
