# T13A 전체 점검과 행렬 요금 준비

## 결정

- 스케줄러 공개 함수/타입 export는 유지하고 `placement-types.ts`에 배치 계약,
  `route-evaluation.ts`에 단일 경로 시간·수단·고정 순서 평가를 분리한다.
  `placement.ts`는 삽입·지리 순서·2-opt·실패 보고를 조합한다.
- `createTaxiFareEstimator`는 계산 중 같은 출발 instant/시간대/프로필의 요금 준비를
  재사용한다. 행렬 하나에 인스턴스 하나를 만들며 실제 출발 시각 재조회는 매번 별도다.
  거리·시간의 유한/비음수 검사와 결과 overflow 검사는 매 구간 유지한다.
  첫 DRIVE 계산 전에는 준비하지 않아 빈 행렬/도보 전용 입력의 오류 동작도 보존한다.
- 캐시는 함수 호출 지역에만 존재한다. 외부 응답 저장 범위나 Google 캐시 정책은 바꾸지 않는다.
- 생활 설정 저장소 포트는 `settings/model.ts`가 소유하고 저장소의 기존 타입 export를 유지한다.
- `lib/http.ts`가 private/no-store 응답과 Origin 비교를 담당한다. 각 HTTP 처리기는
  기존 인증 순서, 상태 코드, 메시지, 본문 한도와 Sec-Fetch-Site 검사를 그대로 담당한다.
- 300줄 초과 테스트는 공통 픽스처·검증 도우미와 제공자/캐시 시나리오로 분리한다.
  테스트 이름과 assertions를 삭제하거나 완화하지 않는다.

## 이유

동선 생성의 같은 행렬에서 `Intl.DateTimeFormat` 생성과 심야 할증 검증이 칸마다 반복됐다.
100×100 행렬의 준비 횟수를 10,000회에서 1회로 줄일 수 있으며 공용 단일 요금 공식은 유지된다.
기존 배치 파일의 타입·경로 평가·탐색 분리는 300줄 제한과 서로 다른 변경 이유를 함께 해결한다.
포트 위치와 공통 HTTP 정책 정리는 동작 변경 없이 의존 방향과 정책 변경 지점을 명확하게 한다.

## 대안

- 전역 시간대 포매터/요금 캐시: 수명·메모리·프로필 변경 무효화가 필요하므로 채택하지 않는다.
- 거리·시간별 요금 전체 캐시: 같은 시각의 준비만으로 병목이 해소되므로 불필요하다.
- 스케줄러 휴리스틱 교체나 외부 호출 동시성 변경: 배치 순서/제공자 부하가 달라져 이번 동작 보존 범위를 벗어난다.
- 모든 API를 하나의 처리기로 통합: 서로 다른 인증/본문/오류 계약을 숨기므로 공통인 정책만 추출한다.
- 날짜 열거·검증기 전부 통합: 생활 설정의 1–31일 거부와 내부 일정의 날짜 열거는 계약이 다르므로 유지한다.
