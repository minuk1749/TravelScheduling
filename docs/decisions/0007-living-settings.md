# ADR 0007: 생활 설정 저장과 시간창 재계산 경계

## 결정

- T11은 `/trips/[id]/settings`, `GET/PUT /api/trips/[id]/settings`를 추가한다.
  `PUT` 본문은 `{ revision, settings }`. 소유자·기간·시간대·고정 항목은 요청에서 받지 않는다.
  응답은 `{ snapshot, calculation }`이며 타입은 [model.ts](../../src/settings/model.ts)에 있다.
- 기본 나가는/들어오는 시각, 기본 끼니, 식사 시간대, 택시 정책과 날짜별 덮어쓰기를 저장한다.
  날짜별 null/행 없음은 기본값 상속, `mealSlots: []`는 식사 없음이다.
  끼니 수는 기존 코어의 0/1/2/3 → 없음/점심/점심·저녁/아침·점심·저녁을 사용한다.
  임의 슬롯 집합(`[DINNER]` 등)을 길이로 재해석하지 않는다. 새 입력은 400, 기존 호환되지 않는 데이터는 409다.
- 시각은 분 단위 `HH:mm`, 여행지 IANA 시간대와 날짜를 함께 검증한다.
  날짜별 유효 활동창은 같은 날에 끝나야 하고 DST의 존재하지 않거나 중복되는 시각을 거부한다.
  DB의 초가 0이 아닌 시각은 자르지 않는다. 레거시 식사창 배열 `[start,end]`는 객체로 정규화한다.
- 저장소는 읽기 스냅샷에 repeatable read, 쓰기에 여행 행 잠금과 revision 재검증을 사용한다.
  revision은 설정·기간·시간대·항공편/버퍼·고정 방문의 정규화된 내용 해시다.
  기본 설정과 날짜별 설정을 한 트랜잭션으로 저장하고 같은 날짜의 created_at은 보존한다.
  고정 방문·기존 결과 일정은 수정하지 않는다. 다른 입력 작성자도 같은 여행 행 잠금이 필요하다.
- 입력 즉시 기존 `calculateDayWindow`로 활동·식사창과 항공 버퍼를 다시 계산한다.
  서버도 같은 계산을 검증하고 저장 후 반환한다. 고정 날짜/시각과 체류시간의 활동창 충돌을
  장소 ID와 함께 표시하며 사용자가 설정을 조정한다. 충돌은 정상 도메인 결과로 저장할 수 있다.
- **재계산 범위는 `TIME_WINDOWS`다.** 공항 이동시간은 미반영(계산에는 0분),
  고정 순서·이동수단·영업시간·고정 방문 간 배치와 식사 소요시간은 검증하지 않는다.
  택시 정책은 저장하지만 실제 이동수단을 재선택하지 않는다. 결과 화면에서도 이 한계를 표시한다.
  전체 동선 생성 API는 병행 작업 T12 담당이며 이 커밋의 기준 develop에는 없다.
  **따라서 T11 완료 기준을 전체 동선 재계산으로 해석하면 아직 미충족이다.**
  T12/T13 연결 시 저장 성공 뒤 실제 생성 서비스를 호출하고 전체 충돌을 표시해야 한다.

## 이유

T12의 진행 중인 파일을 수정하거나 별도의 외부 API·스케줄링 파이프라인을 중복 구현하지 않는다.
현재 가능한 계산과 전체 동선 검증을 구분해 부분 계산을 일정 성공으로 오인하지 않게 한다.
날짜별 상속/0끼를 보존하고, 고정 제약을 조용히 옮기거나 동시 편집을 덮어쓰지 않는다.

## 대안

- T12 엔드포인트를 추측해 호출: 아직 계약이 없어 배포된 화면이 실패하므로 제외했다.
- T11 안에서 전체 경로 생성 구현: 병행 작업과 책임·파일이 겹치므로 제외했다.
- 모든 날짜의 실제 값을 펼쳐 저장: 기본값 변경이 기존 상속 날짜에 반영되지 않으므로 제외했다.
- 설정 변경 시 고정 항목 자동 이동/해제: 사용자 결정 요구에 어긋나므로 제외했다.
