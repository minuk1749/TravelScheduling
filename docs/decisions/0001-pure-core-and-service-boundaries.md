# ADR 0001: 순수 계산 코어와 서버 서비스 경계

- 날짜: 2026-11-18
- 상태: 채택 (T1–T7 구조 유지, 후속 포트 구현은 T8 이후)
- 관련 문서: [아키텍처](../architecture.md), [요구사항](../requirements.md)

## 결정

스케줄러와 요금 계산은 순수 함수로 유지한다. DB·Google Places/Routes·캐시는 제공자와
저장소 뒤에 둔다. 서버 일정 서비스가 입력 조립, 대표 시각 행렬, 실제 출발 시각 재조회,
요금 재계산, 제한된 재배치, 저장을 조정한다. 코어는 제공자도 호출하지 않고 이미 계산된
값만 받는다. Auth.js/HTTP 객체와 PostgreSQL 행은 코어에 전달하지 않는다.

T7의 `checkCapacity`는 T6의 `scheduleVisits`를 내부에서 실행해 추천을 검증한다.
단순 시간 합으로 수용량을 결정하지 않는다. `CapacityResult`의 N, 진단과 추천 일정은
API/화면에서도 구분해 유지한다. 수단 고정은 정책보다 우선하며 희망 장소는 고정 없이 넣지 않는다.

후속 코드는 `places`, `travel-time`, `repositories`, `services` 경계로 추가한다.
T7A에서는 기존 인증 SQL 저장소를 옮기거나 런타임 추상화/새 패키지를 만들지 않는다.
문서의 제공자·저장소 타입은 후속 구현을 위한 계약이며 현재 동작으로 표시하지 않는다.

## 이유

실제 키와 DB 없이 배치·수용량·택시 정책을 결정적으로 검증해야 한다. 외부 응답 지연과
재조회 실패를 계산 실패와 구분할 수 있어야 한다. 이미 T1–T7에서 이 구분이 대부분
존재하므로 입출력과 호출 방향을 명확히 하는 것이 이번 점검 범위에 맞는다.

## 대안

- 스케줄러 안에서 Routes를 호출: 재시도·캐시·비동기 오류가 배치 탐색과 결합되고 순수 함수 규칙 위반.
- Route Handler 안에 입력 변환과 재조회 루프 전부 작성: HTTP 없이 같은 파이프라인을 테스트하기 어렵다.
- 공통 저장소/도메인 프레임워크로 즉시 이동: 현재 결함 해결에 필요하지 않고 T7A 범위 밖 리팩터링이다.

## 결과와 검증

T8/T9는 포트를 목으로 대체해 외부 호출 수·누락 요금·장애를 테스트한다. T12는 서비스에서
실제 시각 재조회 후 성공/초과/충돌과 반복 종료를 검증한다. 제공자 계약을 바꾸면 문서와
결정 기록을 함께 갱신한다. 현재 [아키텍처 테스트](../../tests/architecture.test.ts)가 코어의
의존 경계와 계약 예제를 검사하고 기존 스케줄러 테스트가 결정성·성능·제약을 검증한다.
