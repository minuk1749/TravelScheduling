# T22 모바일 결과 화면 (지도 우선 · 장소 카드)

## 결정

결과 화면은 [디자인](../design.md) 6–7절(R2)과 9절 3-1–3-9를 따른다. 지도가 화면 전체를 차지하고, 아래 고정 패널에서 장소 카드를 한 장씩 넘긴다. 카드·지도 마커·강조 구간은 하나의 선택 상태(`{ date, index }`)에서 계산한다.

- **순수 계산과 화면 분리.** SDK와 무관한 계산은 모두 순수 함수다.
  - `apps/mobile/src/result/`: 날짜별 카드·구간·전체 일정 줄(`days.ts`), 충돌 원인(`conflicts.ts`), 제약 수정(`edits.ts`), 표시 문구(`format.ts`).
  - `apps/mobile/src/map/`: 선택·이전/다음·스와이프 목표·강조할 구간·재계산 중 구간(`selection.ts`), 마커·경로 명세(`scene.ts`), polyline 해독·구간 순서 색·도심 밖 판정·곡선·화면 밖 방향(`geometry.ts`).
  - 화면(`apps/mobile/src/screens/result/`)은 이 결과를 그리기만 한다.
- **지도 어댑터.** 화면은 `ResultMapProps`만 알고 지도 SDK를 import하지 않는다. `MapAdapterProvider`가 앱에서는 `GoogleResultMap`(`react-native-maps`), 컴포넌트 테스트에서는 `FakeResultMap`을 주입한다. 결과 흐름이 컨텍스트에서 어댑터를 한 번 읽어 화면에 prop으로 넘긴다(렌더 중 컴포넌트 생성 금지 규칙).
- **계산 흐름.** 최초 계산은 생성 화면(`/trips/[id]/generate`)이 POST로 실행한다. 응답 전에는 지도 위 결과 패널의 요약 줄에 진행 표시를 띄우고, 계산이 끝나지 않은 카드와 구간은 비워 둔다(3-5). 최초 계산이 실패하면 같은 지도와 패널에서 실패 이유와 입력 보존 안내를 보여 주고, 다시 계산하거나 여행 조건을 수정할 수 있다. 결과가 OK·CONFLICT면 같은 응답을 메모리에서 결과 화면에 넘긴다. 결과 화면은 GET `/constraints`로 입력을 읽고, revision이 응답의 `inputHash`와 다를 때만 한 번 다시 계산한다. OVER_CAPACITY면 T23 선택 화면으로 가며, T23의 `동선 보기`는 검증된 응답을 결과 화면으로 넘긴다(`OutcomeFlow`).
- 충돌로 미배치된 희망 장소는 별 마커에서 날짜를 바꾸고, 원인 카드에서 날짜·예약 시각·순서를 수정할 수 있다. 이전 성공 일정에 같은 방문이 있으면 그 날짜의 번호 마커를 유지한다. 범례에서 현재 희망을 선택하면 시트를 보는 동안 현재 장소 정보로 별 마커를 강조한다.
- **수정.** 장소 수정(날짜·시각·순서 고정, 방문 순서, 희망으로 바꾸기), 희망 장소 날짜 추가, 구간 이동수단 바꾸기는 모두 기존 `PUT /api/trips/[id]/constraints` → `POST /api/trips/[id]/itinerary`로 저장·재계산한다. 희망 장소의 목적 날짜는 기존 예약 시각·순서와 함께 장소 수정과 동일한 `parseFixedVisit`으로 확인한다. 다른 날짜가 필요하면 시트에서 오류를 확인하고 다시 고를 수 있다. 응답의 `inputHash`가 저장한 revision과 다르면 표시하지 않는다(T23과 같은 `verifyRevision`). 충돌 원인에 나온 날짜·출발·도착이 저장된 이동수단 고정과 일치하면 그 구간과 수단을 표시한다. 구간을 특정하지 않고 날짜 단위로 보고된 충돌에서는 그날 저장한 다른 이동수단 고정을 시트에서 검토할 수 있다. 사용자가 해제를 선택하면 그 고정만 제외하고 저장한 뒤 다시 계산한다. 저장 직전 제약을 보관해 `변경 취소`(3-8)와 토스트 `되돌리기`를 같은 경로로 처리한다. PUT은 성공했는데 POST가 실패하면 저장된 입력을 유지하고 POST만 다시 실행한다(3-9). 입력이 다른 곳에서 바뀌었으면 다시 계산 전에 입력을 다시 읽는다.
- 빈 날짜의 여유 시간은 생성 응답의 `availableByDate`를 여행 시간대로 표시한다. 가용 구간이 닫힌 날은 “여유 시간 없음”, 이 필드가 없는 이전 응답은 “여유 시간 정보 없음”으로 표시한다.
- 충돌 화면의 ‘여행 전체 이동수단 고정 보기’에서는 어느 날짜에서든 저장한 구간 하나를 골라 해제할 수 있다. 서버가 고정 공항 이동 때문에 다른 날짜의 활동 시간창을 실제로 줄인 경우, 생성 응답의 선택 필드 `airportTransferLimits`가 구간 키·이동수단·예약된 이동 시간창·영향 날짜를 전달한다. 앱은 선택한 날짜에 영향을 준 구간을 먼저 보여 주고 실제 이동 시간과 고정 기준일을 함께 표시한다. 이전 응답은 저장 날짜와 방향을 사용한다.
- 날짜별 지도와 전체 일정은 여행 시간대에서 실제 이동을 시작한 날에 구간을 표시한다. 항공편과 숙소 도착·출발 행은 각각 실제 시각의 날짜에 둔다. 지도 도로선과 이동수단 저장에는 서버가 계산한 원래 구간 키를 유지한다.
- 전체 일정은 각 구간의 대중교통·택시 시간과 요금을 비교하고, 도보 대안이 있으면 함께 표시한다. 서버가 돌려준 대안만 선택해 제약으로 저장할 수 있다. 장소 카드의 도보 구간은 §7에 따라 바꾸기 칩을 생략한다.
- **경로 모양.** T19 `GET …/itinerary/shapes`에 OK 결과의 `inputHash`와 `itineraryId`를 함께 보낸다. 앱은 두 값이 모두 일치하는 응답만 받아 여행 ID·입력 해시·일정 ID별로 화면 메모리에 둔다. 결과가 바뀐 첫 렌더에서 이전 선을 숨기고, 취소한 요청의 늦은 성공·실패를 무시한다. 구간 배열이나 개별 모양의 응답 구조가 손상되면 직선 대체 경로와 재시도 버튼을 표시한다. 정상 형식의 구간에서 모양이 없거나 선 좌표를 해독할 수 없으면 해당 구간만 직선으로 표시한다. 서버가 오래된 ID를 거절하거나 응답에서 ID가 빠져도 경로 재시도가 가능하다. [T19 계약](T19-route-shapes.md)
- **디자인 값.** §4 그림자와 §6–7 배치·카드·마커·경로 값을 `@travel/design-tokens`의 `shadow`, `result`에 추가하고 문서 값과 같은지 토큰 테스트로 검사한다.

## 이유

- 카드 넘김과 지도 강조가 같은 순수 선택 함수에서 나오므로, 카드와 마커가 서로 다른 장소를 가리키는 상태가 생기지 않는다. 지도 SDK 없이 선택·강조 규칙을 단위 테스트할 수 있다.
- 결과 응답을 메모리로 넘기면 같은 입력의 재계산(Google 이동시간 조회)을 피하고, 검증된 응답과 화면이 일치한다(T23 결정과 같은 이유).
- 편집은 기존 T13 제약 API를 사용한다. 생성 응답은 날짜별 가용 구간을 제공하고, 경로 모양 API는 저장 일정 ID를 받아 응답에서 이를 확인할 수 있다. 기존 해시 전용 호출은 최신 저장 결과를 조회한다.

## 대안

- 결과 화면을 열 때마다 POST로 다시 계산: 비용이 들고 응답이 달라질 수 있다. 저장된 최신 일정을 읽는 소유자용 GET은 아직 필요하지 않아 추가하지 않았다([질문](../questions.md#t22-결과-화면-가정)).
- 지도 컴포넌트를 컨텍스트에서 읽어 바로 렌더: React Compiler 규칙(`react-hooks/static-components`)에 걸린다. 흐름 컴포넌트가 한 번 읽어 prop으로 넘긴다.
- 패널을 끌어 높이를 바꾸는 이전 3단 패널: 2026-11-19 사람 결정(R2)으로 쓰지 않는다.

제약 PUT의 응답을 받지 못하면 초안과 같은 작업 ID를 보관한다. 재조회한 값이 초안과 같으면 추가 저장 없이 다시 계산한다. 값이 다르면 최초 쓰기 버전이 유지된 경우에만 같은 ID로 PUT을 재시도한다. 되돌리기는 직접 승인된 PUT이나 현재 revision의 작업 영수증으로 저장 주체를 확인하고, 서버가 마지막 쓰기를 검사할 수 있을 때 제공한다. 쓰기 버전과 영수증을 모두 생략하는 구형 서버에서도 저장과 재계산을 지원하며 되돌리기는 숨긴다. `apps/mobile/tests/result-write-receipts.test.tsx`에서 타 기기의 동일 값 저장, 해시가 이전 값으로 돌아온 경우와 구형 서버 동작을 검증한다.
