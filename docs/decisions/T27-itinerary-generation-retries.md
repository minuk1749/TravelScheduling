# T27 일정 생성 요청과 결과 복구

## 결정

생성 POST는 선택 헤더 `Idempotency-Key`에 소문자 하이픈 UUID 하나를 받는다. 앱과 웹은 한 번의 생성에 UUID를 하나 발급한다. 응답을 끝까지 받지 못하면 같은 키로 POST를 다시 보낸다. 저장한 여행에서 다시 ‘동선 만들기’를 선택하거나 편집 후 새 계산을 시작하면 새 키를 쓴다. 헤더가 없는 이전 클라이언트는 POST마다 계산한다.

### 동시 요청과 저장

각 POST는 소유권을 확인한다. 한 서버에서 같은 소유자·여행·요청 ID의 계산이 진행 중이면 후속 요청은 그 실행 결과를 기다린다. DB 연결은 첫 요청만 빌리고, 실행이 성공하거나 실패하면 메모리에서 항목을 지운다.

서버 간에는 여행 ID와 요청 ID 조합으로 PostgreSQL 세션 advisory lock을 획득한다. 대기하던 서버는 잠금을 얻은 다음 현재 소유자·여행·요청 ID로 저장 행을 조회한다. 이미 완료된 행이 있으면 처음 저장한 일정 ID, 입력 해시와 결과를 반환한다. 재시작을 거친 재전송에도 같은 규칙이 적용된다.

잠금을 보유한 연결에서 입력 스냅샷 읽기, 도시 프로필 조회, 일정 저장을 수행한다. 제공자를 기다리는 동안 여행 행 잠금과 SQL 트랜잭션을 열어 두지 않는다. 저장 시 기존 여행 행 잠금 아래 소유자와 입력 해시를 재검사한다. 요청 키, 결과 JSON과 정규화 일정은 함께 커밋된다. 저장 전 실패하면 다음 재시도가 다시 계산할 수 있다. 연결 종료 시 PostgreSQL이 세션 잠금을 해제한다.

## 이유

마이그레이션 009는 `itineraries`에 `request_id`와 `request_result`를 추가한다. 키가 있는 행에는 여행·키 조합의 고유 인덱스를 적용한다. `request_result`에는 소유자에게 보낸 계산 결과 DTO를 보관한다. 공유 결과의 표시용 복원은 충돌 당시의 전체 수용량 진단과 날짜별 가용 시간 등 일부 필드를 생략하므로, 요청 재전송에서 이를 사용하면 응답이 달라진다. 장소 상세, Google 원본 응답, 경로 모양은 추가로 수집하지 않는다. 여행 삭제 시 일정과 함께 복구 정보도 삭제된다.

## 대안

입력 해시만으로 요청을 합치면 사용자가 같은 입력으로 새 일정을 만드는 동작을 구분할 수 없다. 서버 메모리만 사용하면 다른 인스턴스에 도달한 재시도와 커밋 직후 재시작을 처리할 수 없다. 클라이언트는 진행 중인 동작의 키를 화면 메모리에 유지한다. 앱과 웹은 재시도 응답을 받은 뒤 저장된 입력을 다시 조회한다. 조회가 실패하면 같은 키로 재시도할 수 있다. 해시가 달라졌으면 입력 변경을 안내하거나 현재 입력으로 재계산한다.
