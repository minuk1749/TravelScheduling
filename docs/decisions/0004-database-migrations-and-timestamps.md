# ADR 0004: 마이그레이션 이력, 행 시각과 일정 생성 순서

- 날짜: 2026-11-18
- 상태: 채택 (T8A)
- 관련: [아키텍처 §5](../architecture.md#5-저장-형식시간대-변환), [T8A 인계](../t8a-handoff.md)

## 결정

`npm run migrate`는 기존 `pg`와 `tsx`로 실행한다. 001부터 연속된 `NNN_name.sql`을 정렬하고
현재 스키마의 `schema_migrations`에 파일명·SHA-256·적용 instant·`applied/baseline`을 기록한다.
이력은 파일 목록의 연속된 앞부분과 일치해야 하며 변경/누락은 실패한다. 재실행은 이력이나 데이터를 바꾸지 않는다.
DB/스키마별 트랜잭션 advisory lock을 획득한 뒤 모든 미적용 SQL과 이력을 한 트랜잭션으로 처리한다.
중간 실패 시 이번 실행 전체를 롤백한다. 실행기에 전달하는 클라이언트는 활성 트랜잭션이 없어야 한다.
SQL 파일에는 트랜잭션 제어나 트랜잭션 밖 명령을 넣지 않는다.

이력이 없는 기존 001–003 DB는 버전별 스키마와 비교해서 자동 등록한다. 별도 임시 스키마에 기존
SQL을 순서대로 실행하고 모든 기존 모델 테이블의 열 이름·타입·NULL·기본값·제약조건을 대조한다.
일치하는 prefix만 등록하고 검증 스키마는 SAVEPOINT로 롤백한다. 일부만 적용됐거나 구조를 수동으로
바꾼 DB는 중단한다. 관계없는 추가 테이블은 비교 대상에서 제외한다. 검증용 스키마 생성 권한이 필요하며
기존 DB 최초 이관 중에는 앱 쓰기를 멈춘다. baseline 시각은 과거 SQL 실행 시각이 아니라 등록 시각이다.
앞으로의 마이그레이션은 반드시 실행기를 사용하며 이력 없는 자동 등록은 기존 001–003에만 제공한다.

004는 누락된 FK 선두 인덱스를 추가한다. 이미 있는 `(trip_id, date)` 등 PK/UNIQUE 인덱스는 재사용한다.
사용자 소유 테이블 전체에 생성·수정 instant를 두고 `NOT NULL DEFAULT now()`를 사용한다.
기존 `users.created_at`은 보존하며 기록이 없던 과거 시각은 이관 시각으로 채운다.
모든 사용자 소유 테이블과 공유 장소의 수정 시각은 DB `BEFORE UPDATE` 트리거가
`statement_timestamp()`로 갱신한다. UPSERT와 같은 값 UPDATE도 쓰기 문장의 시각을 기록한다.
수정 시각은 충돌 검사용 버전이 아니며 자식 변경을 부모로 전파하지 않는다.
도시 프로필의 기존 `updated_at`은 요금 출처 갱신일이므로 자동 변경하지 않고 호출자가 계속 제공한다.

일정은 삭제·덮어쓰기 대신 여러 스냅샷을 보존한다. `itineraries.generation`은 전역 bigint identity이며
여행별로 `ORDER BY generation DESC LIMIT 1`인 결과를 최신으로 선택한다. 같은 트랜잭션의
`created_at`이 같아도 구별된다. `(trip_id, generation DESC)` 고유 인덱스를 추가한다.
기존 일정의 실제 과거 순서는 알 수 없어 이관 번호는 그 순서를 의미하지 않는다. 최신 상태가 중요하면
다시 생성한 결과를 사용한다. identity는 번호의 빈틈을 허용하고 INSERT 순서만 나타낸다.
T12 저장소는 여행 행 잠금과 입력 해시 재검증으로 같은 여행의 동시 저장/오래된 계산 결과를 제어한다.

CI 파일은 보호돼 있으므로 수정하지 않는다. 기존 `npm test`가 부르는 인증·여행 SQL 테스트의 준비를
새 실행기로 전환하고 별도 통합 테스트에서 실제 CLI를 호출한다. 테스트는 `DATABASE_URL`의
PostgreSQL 16을 사용하고 연결 실패를 건너뛰지 않는다.

## 이유

기존 002/003 SQL은 재실행할 수 없고 적용 여부도 저장되지 않았다. 파일 변경 감지와 기존 DB
검증을 실행기에 모으면 새 DB와 기존 데이터 모두 같은 경로로 관리할 수 있다. 전체 실행을 원자적으로
처리하면 실패 후 일부 이력만 수동으로 보정할 필요가 없다. 일반 SQL 인덱스를 사용하므로 트랜잭션 안에서 실행한다.
DB 트리거는 인증 UPSERT, 후속 API와 직접 SQL이 모두 일관되게 수정 시각을 남긴다.
생성 시각만으로는 동시 생성 순서를 구별하기 어렵고 수정 시각은 과거 일정 수정에 따라 바뀐다.
증가 번호는 생성 시각의 충돌 없이 하나의 최신 결과를 고를 수 있다.

PostgreSQL 16의 [트랜잭션 advisory lock](https://www.postgresql.org/docs/16/explicit-locking.html#ADVISORY-LOCKS)과
[현재 시각 함수](https://www.postgresql.org/docs/16/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)의 의미를 따른다.

## 대안

- 기존 SQL에 `IF NOT EXISTS`를 추가: 부분 적용·파일 변경을 숨기고 이력도 남기지 않는다.
- 사람에게 마지막 적용 번호만 입력받기: 온전한 스키마인지 검증하지 못하고 자동 이관 요구를 충족하지 않는다.
- 마이그레이션마다 커밋: 실패 전 단계는 유지되지만 이번 소규모 DB 정비에서는 전체 롤백이 더 단순하다.
- 새 ORM/마이그레이션 패키지: 기존 SQL·pg로 필요한 기능을 충족하므로 추가하지 않는다.
- 애플리케이션에서만 수정 시각 설정: UPSERT나 SQL 경로마다 누락할 수 있다.
- `created_at DESC, id DESC`: 같은 시각의 임의 UUID 순서는 INSERT 순서가 아니다.
- 현재 일정 boolean/포인터: 현재 행 전환과 동시성 처리가 추가로 필요하다. 최신 INSERT 정의에 증가 번호를 사용한다.

## 검증

[마이그레이션 테스트](../../tests/migrations.test.ts)가 빈 DB, 기존 prefix 각각의 데이터 보존,
두 번 실행, 기존 이력 이후 적용, DDL·DML·이력 롤백/재시도, 잘못된 스키마/체크섬/이력, 동시 실행을 검증한다.
[기반 스키마 테스트](../../tests/database-foundations.test.ts)가 전체 FK의 카탈로그 인덱스 검사,
사용자 소유 테이블의 시각 타입·기본값·트리거/UPSERT와 출처 갱신일 보존, 같은 생성 시각의 최신 일정을 검증한다.
