# ADR 0006: T10 여행 입력과 생성 경계

## 결정

- `/trips/new`는 여행 → 항공 → 숙소 → 장소의 4단계 클라이언트 폼이다. 입력은 메모리에만 두고
  완료 시 인증된 `POST /api/trips`로 한 번에 저장한다. 입력 페이지 자체는 정적 공개 화면이며
  검색·프로필 조회·저장은 인증이 필요하다. 홈의 생성 링크는 로그인 사용자에게 표시한다.
- [공유 검증기](../../apps/server/src/trips/input.ts)는 단계별 클라이언트 검사와 전체 서버 검사를 수행한다.
  요청에서 ownerId와 Google 상세 필드를 버리고, 소유자는 세션에서 가져온다.
  현지 항공 일시는 여행 IANA 시간대와 Temporal `disambiguation: reject`로 검증한다.
- T10 생성 DTO `TripDraft`는 Google ID 기반이다. 기존 아키텍처의 `TripInputs`는 DB UUID와
  생활 설정까지 포함하는 **후속 스케줄러 입력 스냅샷** 계약으로 유지한다. 생성 DTO를 그대로
  `saveInputs`나 스케줄러에 전달하지 않는다.
- [생성 저장소](../../apps/server/src/repositories/trip-inputs.ts)는 여행과 항공·숙소·장소 연결을 한 트랜잭션으로
  저장하며, places에는 Google ID만 쓴다. 이름·주소·영업시간·검색 결과는 저장하지 않는다.
  코어/UI `WISH`는 DB `WISHLIST`로 변환한다. 기존 여행 수정·로드는 T11/T12에서 구현한다.
- 기간은 1–31일, 도착 항공은 첫날·출발 항공은 마지막 날, 숙소는 모든 숙박일을 겹침 없이
  덮는다. 당일 여행은 숙소 없이 입력 가능하다. 방문 장소는 1–100개, 체류시간은 정수 1–1,440분이다.
  `luggageOption`은 `VIA_LODGING` / `DIRECT_TO_AIRPORT`이며 후자는 마지막 날 직접 공항 이동이다.
- 기본 생활 설정은 09:00–21:00, 점심·저녁, 요구사항의 기본 식사창, 입국 90분/출국 150분이다.
  날짜별 설정과 재계산은 T11/T12로 남긴다.
- `GET /api/city-profiles?cityCode=...`는 DB 프로필 또는 null과 `WHEN_NEEDED` 추천을 반환한다.
  모든 도시에서 기본 정책을 추천하되, 있는 프로필의 비용 효율 기준·대중교통·대기·요금 정보를
  함께 보여 판단을 돕는다. 도시별 우열을 판정할 실제 구간 비교는 T12 책임이다.
  프로필 누락과 조회 실패를 구별한다. 도시 변경이 사용자의 명시적 정책을 덮어쓰지 않는다.
  T4D가 아직 완료되지 않아 실제 10개 도시 요금표를 임의로 채우지 않는다.

## 이유

미완성 입력을 DB에 단계마다 저장할 필요 없이 흐름 2–5를 완결하고 저장 실패 시 입력을 유지한다.
인증된 소유자·공유 검증기·트랜잭션으로 잘못된 부분 여행 생성을 막는다. Google 상세 캐시 제한은
[ADR 0003](0003-places-cache-policy.md)을 유지한다. 31일은 현재 상세 제공자의 날짜 한도와 맞췄다.
정적인 도시명·IANA 시간대 목록과 실제 요금 데이터는 별개이며 출처 없는 금액을 추천하지 않는다.

## 대안

- 단계별 저장: 초안 상태·중단 복구·수정 API까지 필요하므로 이번 생성 작업에서는 제외했다.
- Google 이름을 DB나 localStorage에 저장: 기존 장소 저장 정책과 충돌하므로 선택하지 않았다.
- 전체 `TripRepository` 즉시 구현: 일정 저장·해시·설정 변경까지 확대되므로 T11/T12로 남겼다.
- 도시별 정책을 이름만 보고 다르게 추천: 검토된 데이터가 없으므로 기본 추천임을 명시한다.
