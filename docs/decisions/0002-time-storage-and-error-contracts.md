# ADR 0002: 시간·저장 형식과 도메인 오류의 변환 경계

- 날짜: 2026-11-18
- 상태: 채택 (현재 표현 유지, 어댑터/영속화 보완은 후속 작업)
- 관련 문서: [아키텍처](../architecture.md), [T7 인계](../t7-handoff.md)

## 결정

현지 날짜/시각과 IANA 시간대를 입력으로 보존하고 계산 경계에서 명시적 instant로 바꾼다.
DST의 모호하거나 존재하지 않는 현지 시각은 거부한다. 시간창은 시작 포함·끝 제외이며
수용량은 실제 경과시간으로 계산한다. 택시 심야 요금은 여행 시간대의 출발 시각을 사용한다.

SQL의 `WISHLIST`, numeric 문자열, time의 초, nullable 값과 JSONB는 저장소/입력 어댑터에서
코어 타입으로 검증·변환한다. 기존 데이터를 즉시 마이그레이션해 enum을 통일하지 않는다.
날짜별 null은 기본값 상속, 빈 식사 슬롯 집합은 끼니 없음이다. 슬롯 개수만 세어 `[DINNER]`를
`[LUNCH]`로 바꾸지 않는다. 기존 스키마에 없는 식사 stop 종류·구간 고정 입력·구간 시각 등은
T12/T13 저장 연결 시 마이그레이션을 설계하고 테스트한다.

`OK/OVER_CAPACITY/CONFLICT`는 계산의 도메인 결과다. 사용자 입력 형식 오류, 접근 거부,
외부 장애와 구분한다. 알 수 없는 요금은 null이며 0이나 경로 없음으로 바꾸지 않는다.
일일 최종 경로가 시간창에 들어가지 못하면 `ScheduleResult.issues`에
`{date, reason: 'TIME_WINDOW'}`를 추가한다. 방문 없는 날도 시작/종료가 다르면 이동은 필수다.
가용 창 없는 동일 지점의 빈 날에는 이 오류를 만들지 않는다.

## 이유

현재 SQL과 스케줄러가 서로 다른 표현을 쓰지만 아직 연결하는 코드가 없어, 타입 단언으로
연결하면 잘못된 날짜·끼니·비용이 조용히 전달될 수 있다. 후속 경계의 변환 규칙을 먼저 명시한다.
한편 방문 없는 숙소 간 60분 이동에 가용 시간이 30분뿐인 입력이 기존에는 `OK`였다.
최종 경로 실패가 방문 실패나 issues에 기록되지 않아 수용량 검사가 빈 일정을 성공으로 판단했다.
날짜 수준의 실패를 추가하면 실제 배치 성공 여부에 근거하는 T7의 설계를 유지할 수 있다.

## 대안

- 모든 현지 시각을 서버의 `Date`로 읽기: 실행 머신의 시간대와 DST에 따라 의미가 달라질 수 있다.
- DB enum/JSONB/시간 필드를 일괄 변경: 실제 연결이 없는 단계에서 기존 데이터와 후속 작업 범위를 불필요하게 변경한다.
- 필요시간 하한이 가용시간보다 큰 경우만 차단: 하한은 실제 배치 성공을 보장하지 않으며 날짜별 경로 진단을 놓친다.
- 방문 없는 날의 이동을 생략: 숙소가 바뀌는 날에도 이동 제약을 무시하게 된다.

## 결과와 검증

`issues`의 판별 유니언에 새 사유가 추가된다. 현재 프로덕션 소비자는 `checkCapacity`뿐이며
모든 issue를 실패로 처리하므로 별도 분기 수정은 필요 없다. 후속 UI는 날짜 수준의 시간창
실패를 표시해야 한다. [수용량 테스트](../../packages/core/tests/scheduler-capacity.test.ts)가 초과·창 없음·
정확한 경계·경유해서 들어맞는 경우를 검증한다. 기존 DST·요금 경계 테스트를 유지하고
[SQL 모델 테스트](../../apps/server/tests/travel-model.test.ts)는 사용자 소유 테이블 전부의 삭제와 공유 장소 보존을 검사한다.
